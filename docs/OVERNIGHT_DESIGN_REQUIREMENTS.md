Top-level product navigation remains small: business/profile context, Find customers, and a clear route back to the relevant customer list. ## Screen-by-screen final behavior

### 1. Landing → signup

- State seller and outcome plainly above the fold: this helps founders selling SaaS to businesses identify businesses to approach and manage their own outreach. Current source headline is `From your website / to your next sales conversation.` Keep a clear audience qualifier and concrete supporting sentence so that the abstract second line does not hide what the product does.
- Website input remains the strongest entry point, with a visible persistent label, public-website example, URL-friendly keyboard, and primary CTA. Current landing `Get started` is honest because it opens account setup; `Analyze my website` belongs to the actual analysis step after signup. If wording changes, the action must match it. Explain signup precedes profile review in one short line.
- Keep `Sign up` / `Sign in` as standard labels. Keep manual entry as a quieter, functional alternative under the website form. Both paths preserve per-tab intent through the real auth flow without adding the website to redirect URLs, automatically analyzing it, spending money, or overwriting an existing profile.
- Hero preview shows understandable website → profile → businesses → approved introduction → recorded conversation/outcome. Product examples must be visibly fictional and rendered as accessible HTML, with source/status language matching the real app. No fake users, customer logos, conversion numbers, invented verified emails, swipe controls, carousels, or autoplay-gated content.
- Explain current manual delivery and user-recorded replies/meetings succinctly before a visitor signs up; do not imply inbox/calendar sync or automatic follow-ups. Keep planned capabilities separate from available actions. Public availability copy must match whichever SaaS features actually pass integration tests.
- Keep useful FAQ and privacy/terms/footer links. A decorative background must stay faint and never obscure the form, headline, or focus rings. On 320/390px screens all copy/form/actions reflow without page-level horizontal scrolling.

### 2. Signup → website-first business setup → review

- Use the same brand, paper, typography and button treatment through local entry, Clerk signup, organization choice, and app shell. Real SaaS session/organization/role failures have clear sign-in/team actions. Local review must not be presented as a newly created cloud account.
- Preserve the accepted centered setup layout: `Tell us about your business`, one website card, `Analyze my website`, and quiet manual alternative. Do not send Analyze into the old sidebar dashboard or a visually unrelated form.
- Analyze has a real busy label, blocks duplicate work, preserves input on failure, reports one understandable error, and supports manual fallback. Do not describe homepage extraction as infallible or claim AI analysis if it is rules-based.
- Review stays compact in the same visual shell: company name, what it helps customers do, target customer types; geography/extra targeting is optional. The user can correct everything before saving. Avoid ICP/scoring/campaign vocabulary in this flow. Saving is visible and separate from launching discovery. A read-only member gets an honest admin-managed state and can continue only when a real profile exists.
- Unsaved profile edits must survive internal view changes or trigger a clear save/discard choice before leaving; never silently reset saved data because a new landing URL arrives.

### 3. Discovery form → dedicated progress route

- Prefill from the saved profile while retaining the user's current per-tab target edits. Keep business type, optional location, and a 1–5 result control, default/max 5. Do not silently increase the cap or promise exactly five matches.
- Show useful capability states in plain language; avoid provider configuration jargon in the main journey. Verification being unavailable must not imply discovery is unavailable if published contacts can still be returned.
- `Find customers` explicitly starts the search once. Navigate to the dedicated refreshable result URL, with real queued/running/stage text. Results are not appended below the form. No fake percentages, countdowns, cycling invented companies, or timed success transitions.
- Refresh, browser back, transient poll errors, and `Check status again` read the same job. They never create another paid search. Distinguish `Check existing search` from `Start a new search`. Retain partial real results; suppress raw per-candidate HTTP403 chatter and engine query fragments.

### 4. Customer list → selected outreach or CSV

- Desktop keeps a semantic dense table: selection, company/name+domain, available email, verification status, and concise `Draft message`. Target approximately 64–76px rows; shared dividers rather than separated bulky company cards.
- Preserve the user's rejection of fit explanation lines, scores, unknowns, research-diagnostic columns, and `Research details` in the result rows. Sources/facts remain in the underlying records/CSV and a draft's relevant supporting context. Do not delete evidence to simplify the UI.
- Display only qualified matches according to the existing explicit customer-type/evidence gate; do not count low-relevance scraped pages as leads. Fewer results and zero results are valid. An unobtrusive excluded-candidate count is enough.
- Contact-first sorting means verified email, then published unverified, then missing email, with stable secondary ordering. Keep explicit verification text. Missing email must remain visibly unavailable, not guessed or promoted to verified. Sorting preserves selected IDs; CSV uses selected qualified rows in shown order.
- Table select-all supports mixed state and clear labels. Preserve export. Make `Prepare outreach (N)` the primary next journey action when N=1..5; keep CSV secondary. Only an explicit click creates/opens server-persisted outreach. An uncertain create failure retries the same intent/key, not a second operation.
- At 390px, reflow each semantic row into a compact stacked item with checkbox, company/domain, email/status, and Draft together. At 320px Draft may use a final full-width row beside the checkbox column. No page-level horizontal pan to discover the action; no tiny type. A comparison table must not force the whole page wider than its viewport.
- Draft editing opens a labeled right-side dialog on wide screens and a full/near-full-height sheet on phones. Keep Escape/native cancel, trapped keyboard focus, focus restoration to the precise opener, background scroll locking, cleanup on close/unmount, and selected row state intact. Main editor scrolls above a separate Copy/Reset footer, never beneath an overlay. Use dynamic viewport and safe-area padding. Test short-height/200% zoom as well as nominal phone height; do not claim physical keyboard behavior from desktop emulation.

### 5. Outreach / Review

- Use a compact prepared-business chooser and one editor, not a grid of giant cards. Desktop may use the existing ~250px context column + main pane; phone uses a short chooser (accessible scroll region or equivalent compact selection), then the active editor. Do not let a large headline, three tabs and a tall chooser consume the entire first phone viewport before the user reaches the recipient.
- Show the seller context above and recipient/company context within the editor. Clearly show selected recipient and actual verification status. Edited addresses have no inherited verification claim.
- Persist recipient, subject, body and optional booking link. Loading a saved thread never generates AI. Initial AI generation is an explicit action and reuses the existing cached original; it is not reply generation and not regeneration. An uncertain failure preserves its idempotency key; only a confirmed terminal failure may expose an explicit new attempt with an honest allowance/cost note. Never spend in automated QA.
- Visible sequence: edit → Save changes → Approve exact message → Copy approved message → Record sent externally. The screen shows the current state and a clear next action rather than five equally emphasized buttons. No automatic step advancement or automatic copy/send.
- Every local edit immediately disables readiness; server-saved content changes invalidate approval. Approval refers to exact recipient/subject/body/booking link and current reply context. Copy includes the optional booking link in the same representation as immutable external-send history. An approval cannot authorize later-edited content.
- Keep `No mailbox is connected` / manual-send explanation concise but visible. Record sent externally is a user assertion only, never proof of delivery or an outbound transport. Blocked states explain why actions are disabled. Do not expose provider keys/internal implementation details in the form.

### 6. Conversations

- Show chronological saved inbound/outbound entries with explicit `received reply · pasted by you` or `sent externally · recorded by you` provenance. Keep full text readable/wrappable; modest compact bubbles/rows are sufficient.
- Pasting a reply saves real user-entered content, clears old response approval, and requires reply-status review. Support Interested, Has a question, Not now, Not interested, Opted out, Uncertain, Needs review with plain labels. Initial threads have no inbound message, so their default `awaiting_review` status must not block the first introduction or mask Approved/Sent states in the chooser.
- Reply editing is human-written in the current contract. Do not reuse an introduction generator and label it an AI reply. Keep it human-written until a new conversation-grounded backend contract, the spending guard, and independent review pass. Implementing that guarded copilot is part of the overnight technical/product priorities; enable it only after those gates are met.
- Needs review/uncertain/not-now/not-interested block readiness; pause also blocks it. Opt-out suppression remains sticky across classification correction, recipient changes and matching company threads. Make opt-out unmistakable and disable prohibited actions; a cosmetic status change cannot unsuppress it.
- Preserve unsaved local text while switching company/view, or show a real save/discard choice. Disable editing while a save is in flight, or merge late saves without losing new keystrokes. Never silently clear an unsaved response when changing another status.

### 7. Meetings and customer outcomes

- Keep the third view small: optional existing booking link, user-reported meeting state, user-reported customer outcome. Do not add a calendar UI or analytics dashboard.
- Saving/copying a link or recording a sent message does not book a meeting. Distinguish Not recorded, Booked, Attended, No show, Cancelled. Customer outcome is separately Not recorded / Became a customer / Did not become a customer. All are labeled `reported by you` until a real integration can establish otherwise.
- Preserve records on refresh and between views; show save failures without optimistic false success. Do not imply attendance caused a sale or require a sale outcome just to leave the screen.

## Cross-cutting interaction states

For every data-dependent screen, implement and visually inspect initial loading, existing-data loading, saved success, empty, partial, offline/transient error, authorization failure, and stale/revision conflict. Errors should say what the user can safely do next. A refresh/retry of an existing resource must not create a new job or spend again. Keep readable real data while a noncritical refresh fails. Never toast `Saved` before server acknowledgement.

Use persistent visible labels and programmatic error associations; focus the invalid field or error summary where appropriate. Loading/status announcements use restrained live regions, errors use alerts, and lengthy changing lists do not spam announcements. Include a skip link and logical landmarks/headings. If using actual ARIA tabs, implement the full keyboard pattern; otherwise use correctly labeled navigation buttons with active state, as the current outreach views do. Selection is not communicated only through green tint.

Motion remains purposeful and finite: brief 150–250ms focus/hover/sheet transitions, existing short intro, subtle Analyze-button border glint, and once-only viewport-triggered website/profile/result reveal. No looping attention animation or fake live activity. Any persistent motion over five seconds needs a usable pause control; prefer finite motion. `prefers-reduced-motion` must remove decorative transforms/animations and smooth scrolling, leave all content visible, and preserve loading information as text. Do not hide essential content until IntersectionObserver or JavaScript runs.

Check the app with keyboard alone: signup through setup; input errors; select-all mixed state; sorting; each company-specific Draft trigger; dialog open/Tab/Shift+Tab/Escape/close/focus return; outreach company switching; Save/Approve/Copy/record; reply-status selection; meeting outcome editing. Check native dialog StrictMode mount/unmount and sequential editors, because scroll/focus cleanup already caused real regressions in this work.
