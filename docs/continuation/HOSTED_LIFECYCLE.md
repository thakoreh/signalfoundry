# Hosted manual lifecycle — source implementation, still gated

These internal Convex functions extend HOSTED_LEDGER.md, using its same disabled-by-default flag, authenticated admin mutation/tenant read wrappers, organization intent, revision/idempotency and exact approval boundaries. No new service/dependency, provider operation, scheduler, deployment or account connection. Public hosted outreach REST remains503; this is **not complete hosted parity or rendered/provider acceptance**.

## Operations and facts

- `outreachLifecycle.refer` requires the actual latest received referral and current parent revision. It creates a separate same-company, user-entered/unverified contact with referrer name/message/thread credit, copied public company context and fresh empty contact basis/approval. Canonical-company duplicate addresses, original recipient, bounced/suppressed targets and100-thread overflow are refused. Replays return the child's current safety state. Parent received text remains immutable.
- `planFollowup` follows an explicitly reported initial send to the original recipient, at most twice. Each plan has its own original offset+IANA time, future weekday at least3 business weekdays after the last reported send, saved text and later exact due approval. This weekday rule does not model public holidays or claim an optimal send time. Copy/Open/preflight consumes no send count. Every inbound or meeting permanently stops cold work; correcting classification or resuming never reinstates it. An explicit pause clears the pending plan/approval, retaining audit; replan explicitly after resume if still eligible.
- `reportMeeting` records time/zone/recipient and an append-only reported event. The same UTC instant, including a zone correction, retains its version. Rescheduling changes version. A booking cannot move to an edited recipient. It pauses pending siblings until an explicit founder decision and new approval, without clearing suppression.
- `prepareConfirmation` requires a future current booking, matching recipient and no recorded confirmation for that version. It only saves a draft; ordinary exact approval and manual report remain separate. Every reported outbound stores immutable purpose/date/booking-version metadata. A second confirmation is refused; after the meeting time, report the outcome instead.
- `reportOutcomes` keeps manually reported booked/attended/no-show/cancelled and won/lost/unknown distinct. Attendance/no-show require the reported time to have passed. No ignored prompt changes state; meeting is not sale. Corrections append events instead of rewriting history. Planning/event history is bounded200/thread; messages remain bounded50.

`outreachLedgerStore` centralizes the same owned transaction/view/admission logic across core, lifecycle and activity modules. Registered existing functions remain present. Optional schema expansion does not rewrite old approval or actual-sent snapshots. New binding includes lifecycle/booking-link bytes; older pending approvals require fresh review, never silent restoration.

## Time, returning work and metrics

Timed Copy/Open must use `outreachLifecycle.preflightManualAction`, a **read-only, uncached mutation transaction**. It recomputes actual server time, revision, approval identity, suppression, basis, sender and company state with no sent/request/event write. The older query preflight is retained for untimed compatibility but refuses timed purposes; a cached query cannot authorize an expired confirmation. Reported sends independently recheck these rules.

`outreachActivity.nextUp`/`insights` require a bounded current `clockBucket` argument to invalidate cached queries as time passes. It is cache input only: server time determines due/expired work, and a future caller bucket grants no early approval. The future hosted UI must advance/refetch that bucket at least each minute and on focus; it is not implemented by passing a static number. No actual remote subscription/cache behavior is claimed from convex-test.

The bounded queue returns at most20 tasks, one/thread, from at most100 saved threads: reply review/answer, due followup, manual action, pending draft, planning and after-time meeting question. Future snoozes defer contact, but **never hide a meeting outcome already due**. The same defect was reproduced and repaired in local SQLite's queue; both have permanent controls, including an actual loopback HTTP fixture. Neither prompt assumes attendance or resumes snoozed outreach.

Activity is derived from immutable messages on successful mutations, not from approval/open/copy. Read-only projections do not scan every message on every home read. Unique-company funnel counts are explicitly reported-by-you, do not force a nested funnel, exclude OOO/bounce from replies and exclude demo/unknown provenance. Company contact/suppression/pause markers and future dates support the next batch/departure without research or paid work.

`outreachActivity.repairActivity` is an internal admin operation with explicit organization intent and a3-thread paginated batch. It derives old activity from actual history, recovers eligible public company context from owned source research, and invalidates pending approval/revision. It never manufactures sender identity, contact permission, provider evidence or a new send. Existing projected rows are skipped. Legacy unknown history is shown as review work, excluded from claims until reconciled. Do not call this against owner/cloud data without separate operational authority.

Hosted start now applies the same explicit non-demo/customer-type≥60/no-exclusion/public-company-evidence predicate as local discovery/drafts; geography alone cannot compensate. This is a bounded rule gate, not proof of intent, semantic accuracy, real email verification or customer demand.
